# Rapport de dysfonctionnement et correction

## Incident ID
INC-2026-11-16-07

## Date
2026-11-16T18:40:00.930Z

## Observed Symptom & Impact
- **Symptom**: l’instance n8n est indisponible (HTTP 502/503). Tous les probes (Roster, Bridge, Memory, Vec, Content, REST, n8n) échouent.
- **Impact**: les workflows ne s’exécutent plus, les webhooks sont bloqués, et aucune tâche automatisée ne se lance.

## Root Cause Analysis
### 5 Whys
1. **Pourquoi** n8n ne répond pas ? → le processus n8n a quitté de façon inattendue.
2. **Pourquoi** le processus a‑t‑il quitté ? → exception critique liée à la connexion à la base de données PostgreSQL.
3. **Pourquoi** la connexion a‑t‑elle échoué ? → le service PostgreSQL était hors ligne (timeout de connexion).
4. **Pourquoi** PostgreSQL était‑il hors ligne ? → arrêt manuel de la base de données pour maintenance sans mise à jour du fichier `.env`.
5. **Pourquoi** le fichier `.env` n’a‑t‑il pas été mis à jour ? → absence d’automatisation de déploiement et de test de la variable `DATABASE_URL`.

## Applied Fix & Verification
- **Redémarrage** de PostgreSQL : `sudo systemctl restart postgresql`.
- **Redémarrage** de n8n via PM2 : `pm2 restart n8n`.
- **Mise à jour** du fichier `.env` avec la bonne URL de base de données et vérification de la disponibilité de PostgreSQL.
- **Surveillance** introduite : script de health‑check qui vérifie la connexion DB et l’état du processus n8n toutes les 30 s.
- **Test** manuel : déclenchement d’un workflow simple ; succès confirmé.
- **Documentation** ajoutée au répertoire `Rapport de dysfonctionnement et correction` pour référence future.

## Next Steps
- Implémenter une alerte Slack/Discord pour chaque incident de type `DOWN`.
- Ajouter un test automatisé de santé dans le pipeline CI/CD.
- Envisager la mise en place d’un cluster PostgreSQL haute disponibilité pour éviter ce type d’incident.
